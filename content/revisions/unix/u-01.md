## 개정 범위와 판단

root 원격 직접 로그인을 차단하고 개인별 관리 계정으로 작업자를 구분한다. `/etc/securetty`는 SSH 접근 통제 근거가 아니다.

## 배포판별 적용

RHEL 10의 SSH unit은 일반적으로 `sshd.service`, Ubuntu 26.04 LTS와 Debian 13은 `ssh.service`이다. 설치된 unit과 socket 활성화를 직접 확인한다. 세 배포판 모두 주 설정과 포함 파일의 유효 값을 기준으로 판정한다.

## 점검 절차

`sshd -t`와 `sshd -T`로 구문과 유효 `permitrootlogin` 값을 확인한다. `Include`와 `Match`가 있으면 실제 관리 사용자·접속 주소 조건을 넣은 `sshd -T -C` 결과도 확인한다.

다음은 서버에서 관리자 권한으로 실행하는 읽기 전용 점검 예시다. `192.0.2.10`은 실제 관리 클라이언트 주소로 바꾼다. 호스트명이나 로컬 주소를 조건으로 사용하는 `Match`가 있으면 그 조건도 `-C`에 제공한다.

```bash
sudo /usr/sbin/sshd -t
sudo /usr/sbin/sshd -T -C user=root,addr=192.0.2.10 | grep '^permitrootlogin '
systemctl list-unit-files 'ssh*'
systemctl list-sockets --all
```

출력은 `permitrootlogin no`여야 한다. `prohibit-password`는 root의 공개키 로그인을 허용하므로 직접 로그인 전면 차단과 같지 않다.

## 조치 절차

유효 설정에 `PermitRootLogin no`를 적용한다. 먼저 별도 관리 계정의 키 인증과 권한 상승이 가능한지 확인하고 기존 세션을 유지한 상태에서 설정을 검증한 뒤 SSH 서비스를 reload한다.

현재 `Include` 순서를 확인한 후 관리되는 설정 파일에 다음 값을 반영한다. OpenSSH는 일반적으로 먼저 얻은 값을 사용하므로 뒤쪽 파일에 같은 키를 추가하는 방식으로 적용을 추정하지 않는다.

```text
PermitRootLogin no
```

## 영향과 검증

root로 접속하는 백업·자동화는 전용 계정으로 이전해야 한다. 별도 새 연결의 정상 로그인과 root 거부를 확인하기 전 복구 세션을 닫지 않는다.

Verification required: 대상 배포판 VM에서 변경 전후 동작과 복구 절차를 검증해야 한다. 이 문서는 원문과 분리된 개정 초안이며 운영 적용 또는 사람 검토 완료를 의미하지 않는다.
