## 개요

### 점검 내용

SNMP 접근 제어 설정 여부 점검

### 점검 목적

SNMP 접근 제어 설정을 통해 비인가자의 접근을 차단하기 위함

### 보안 위협

SNMP 서비스에 접근 제어가 설정되어 있지 않을 경우, 비인가자의 접근, 네트워크 정보 유출, 시스템 및 네트워크 설정 변경, DoS 공격 등의 위험이 존재함

## 점검 대상 및 판단 기준

### 대상

RHEL 10, Ubuntu 26.04 LTS, Debian 13

### 판단 기준

- **양호:** SNMP 서비스에 접근 제어 설정이 되어 있는 경우
- **취약:** SNMP 서비스에 접근 제어 설정이 되어 있지 않은 경우

### 조치 방법

승인 수집기의 네트워크 접근 및 필요한 OID의 읽기 전용 권한 적용

### 조치 시 영향

view 축소 시 일부 지표 누락 가능. 필요한 지표 및 trap 알림 범위 확인

## 점검 및 조치 사례

### RHEL 10

1. SNMP 패키지 및 실행 역할 확인

   ```bash command
   rpm -q net-snmp
   systemctl cat snmpd.service
   systemctl status snmpd.service snmptrapd.service
   sudo ss -lnup
   ```

2. 네트워크 및 OID 권한 확인

   역할별 `/etc/snmp/snmpd.conf.d/monitoring.conf`로 분리할 때 실제 주 설정에 `includeDir /etc/snmp/snmpd.conf.d` 연결. 이 경로의 자동 포함을 전제하지 않고 기존 includeFile·includeDir 및 실행 인수의 설정 경로 대조. includeDir는 `*.conf`를 읽지만 순서를 보장하지 않으므로 파일 번호로 우선순위를 조정하지 않고 중복 접근 정책 제거. 분할 파일도 서비스 계정의 필수 읽기 권한을 보존하며 비인가 읽기·쓰기 차단. `/etc/snmp/snmpd.conf`의 agentAddress와 view·group·access·rouser·rwuser를 대조하여 수신 주소, 보안 수준, 읽기·쓰기 범위 확인. include 파일과 실행 인수의 별도 설정 확인

3. 수집 OID의 읽기 전용 view 적용

   ```text configuration
   view monitoring included .1.3.6.1.2.1.1
   rouser monitor priv -V monitoring
   ```

4. 수집 범위 및 출발지 제한

   예시 view는 system subtree만 포함하므로 필요한 지표 OID만 추가. monitor를 실제 v3 사용자로 대체하고 기존 광범위한 rouser·rwuser·access 항목 정리. 현재 방화벽 관리 도구에서 승인 수집기만 UDP 161에 접근하도록 기존 규칙 제한. trap 수신은 별도 승인 송신기의 UDP 162 범위로 관리

5. 구성 적용 및 서비스 확인

   ```bash command
   sudo systemctl restart snmpd.service
   systemctl status snmpd.service
   sudo ss -lnup
   ```

6. 수집 지표 및 비인가 권한 차단 확인

   정상 수집기의 필수 지표 존재 여부와 쓰기 권한 미부여 확인. 허용되지 않은 OID 및 네트워크에 대한 거부 정책 확인. IPv6와 외부 방화벽도 동일 범위로 대조
